# awp-update — maintainers' notes

Current: **awp-update v2.1** (engine: awp-generate v2.2). No libraries: the skill reads and writes an engagement workbook only.

`scripts/update.py` holds the read / plan / apply logic. It reads the workbook with `export_spec` from `awp-generate/scripts/awp.py` (which `release.py` copies into the zip next to `update.py`) and edits the 100 and 200 sheets in place; only a test sheet whose steps change is laid out again, with the engine's `build_test`.

## Release
`python release.py awp-update <version>` from the repository root → `dist/skill-awp-update-<version>.zip` and `dist/copilot-awp-update-<version>.zip` (this folder + `scripts/awp.py`; no `lib/`). Before tagging: `python awp-update/scripts/update.py selftest`, then one full run on `awp-generate/ref/example.xlsx` saved once by a spreadsheet application (so formulas carry cached values), with staff responses and side notes typed in, using the worked example in `ref/update.md`: `apply` must print `VERIFY PASSED`, every sheet without changes must be cell-for-cell identical to the input, and the notes must still be there. Repeat on a workbook built by awp-generate 2.1 (questions at the foot of each 200 sheet). Release again whenever awp-generate's engine changes the layout of the 100, 200 or 300 sheets.

## Design decisions (so they are not reopened by accident)
- **The model writes a change list, the script writes the workbook.** Cell-by-cell editing by a model is what times out and what drifts from the format. An update file is small, reviewable and re-runnable.
- **Edit in place, do not rebuild.** v1 rebuilt each changed sheet from its exported content; on a real engagement workbook that meant stopping for every note the team had typed outside a table cell. v2 locates the rows with the same header-driven logic as `export_spec`, writes only the cells that change, and inserts or deletes single rows (carrying merged cells and row heights). The team's notes, comments and highlighting are never in the way. The cost is a second place that knows the 100/200 column headers (`locate_rcm`, `locate_wt`): keep them in step with `export_spec`.
- **Nothing is lost silently.** What a script save cannot keep (embedded files, threaded comments, pictures without Pillow) and what a re-laid test sheet holds outside its tables are listed and stop the update unless the user accepts with `--force`.
- **The walkthrough questions and responses are read-only.** They are the team's record; there is no change type for them. `show` prints them, together with any text typed beside the tables and any comment, as evidence. The one write is clearing the Control Reference of a question whose control was removed.
- **Every change needs a source and a basis**, and all of it goes to an update log beside the workbook. The log is a separate file so the workbook's structure stays the house structure.
- **Row numbers in update files are the original workbook's.** All files are applied in one `apply`; renumbering happens once at the end. Control numbers never change; new controls take the next free number on their sheet.
- **Rows are rewritten, rarely removed.** A planned control the client lacks is a design gap to record, not a row to delete; `remove_activity` exists for activities that do not exist at the client and cleans the references it leaves behind.
- **The RCM follows the test.** When a test's steps change, the RCM row that quoted the full steps is updated with it; rows that quote selected steps are flagged by the engine's validator.
- **Expected becomes actual, enforced in code.** Planning labels ("Expected: …", "Expected process") are detected by pattern: `show` tags them, the still-open list reports them, and `check` refuses new text that keeps one. The pattern matches labels, not the ordinary word ("arrears are expected to be settled" in a library background is not a label). Rows the sources do not cover keep their label on purpose.
- **The rows follow the process, enforced by a declaration.** A model left alone rewords the draft's rows and keeps their number. Each update file must therefore list the actual process steps of the sheet (`process`); `check` reports rows before and after against that list and warns on a mismatch. A warning, not an error: one step can legitimately carry two controls.
- **Older workbooks are brought to the 2.2 layout on apply.** `migrate_questions` moves each sheet's question block to the questions tab by header text, so columns the team inserted (an interviewee's notes column, say) and notes around the table go with it. The questions keep their own numbers per sheet.
- **Out of scope for now:** recording test work (300 series) and conclusions; harvesting (awp-learn).
