# awp-generate — internal-audit work program (AWP) builder

**Use this skill when** an auditor asks to prepare the AWP, build the work program, set up the workpapers, create the RCM / walkthrough / test sheets, or wants the blank template — for any client and any process.

**What it produces:** one Excel workbook, identical structure and formatting every time: `Scope`, index `A`, `A100` risk and control matrix, `A200` + `A201…` process walkthroughs (activities, controls, walkthrough questions), `A300` + `A301…` one sheet per test with the work-done table, `A400` data-analytics plan. Numbering: 100 = RCM (partner's page), 200 = process and control documentation from the walkthrough, 300 = testing, 400 = DA. The series letter (`A`, `E`, …) is a setting.

Everything is generated by `scripts/awp.py`. Never restyle, renumber or hand-patch a workbook: change the input and rebuild.

---

## The three layers (what you may touch)

| Layer | Files | Who changes it | How |
|---|---|---|---|
| 1 Structure | `SKILL.md`, `scripts/awp.py`, `ref/*` | Skill owners only | `/awp-release` — never during an engagement |
| 2 Content libraries | `lib/core.json` (universal modules), `lib/pack-<process>.json` (one per process) — shared by every `awp-*` skill | Any team, after human review | the **awp-learn** skill (`/awp-learn` → `apply`) → owner publishes |
| 3 Engagement | The Excel workbook (plus a selection/spec JSON kept with it) | The engagement team | `/awp-build`; edit the workbook freely during fieldwork |

Libraries hold **no client data**: no client, tenant, vendor, system, person, amount, date or prior-year observation. Engagement-specific words enter only at build time through tokens (`{CLIENT}`, `{SYSTEM}` …) and through `prior_year` / `background_additions` in the selection.

Every workbook carries a build stamp on the index sheet (`Built with awp-generate v2.1 · core v1 · pack commercial-leasing v1 · date`; a blank template names only the skill version) and a tiny hidden `_build` sheet (versions, module ids, tokens). Users never need to open it. Cross-references in angle brackets (`Please refer to <A302> …`) are house style, not unresolved links.

## Commands (the user types these — or says them in plain words; you run the script)

Users are not technical and rarely type a slash command. Map what they say to the command, then follow it exactly:

| The user says something like | Command | Never do instead |
|---|---|---|
| "give me the template", "a blank work program", "what does it look like" | `/awp-template` | hand-draw a workbook |
| "prepare / build / set up the AWP (work program, workpapers, RCM, walkthroughs, tests)" | `/awp-build` | write cells by hand |
| "update the skill with what we did", "add what we learned", "save this for the next team", "improve the library from this project" | not this skill: tell them to run the **awp-learn** skill on the finished AWP (its zip is `skill-awp-learn-<version>.zip`) | edit `scripts/awp.py`, `SKILL.md`, the `ref` files, or hand-edit a library; produce a new release zip |
| "change the format / add a column / rename a sheet / fix the script" | decline: Layer 1 belongs to the skill owners (`/awp-release`); tell them what to ask the owners for | change Layer 1 |

Whatever the words, the deliverable of `/awp-build` is the workbook (plus its selection and spec JSON). A new zip is never the deliverable of an engagement session.


Work inside the folder that contains `SKILL.md` (the zip unpacks to `awp-generate/`; the script finds the libraries in `lib/` next to it, so absolute paths and other working directories also work). Keep the engagement's files **outside** the skill folder — `../work/` for the material, selection and spec, `../out/` for what you deliver — so client documents never sit inside the skill folder. Run `python scripts/awp.py selftest` once per session before the first real command (`python3` if `python` is not found). It must print one line starting `SELFTEST PASSED - awp-generate v2.1 · core vN · pack … vN` and report those versions to the user. If it fails, fix the environment (needs Python 3.6+ and `openpyxl`, nothing else).

### `/awp-template` — blank workbook, no engagement material
`python scripts/awp.py template "AWP template.xlsx" --tests N --walkthroughs N` (defaults 3 and 2; ask, or use 12 tests and 6 walkthroughs for a full-size process). Every cell that needs content shows a `[placeholder]` describing what belongs there. Verify with openpyxl that the sheet list is `Scope, A, A100, A200, A201…, A300, A301…, A400` with the counts asked for, then deliver the file and say in two lines what it contains and that every `[placeholder]` is to be replaced. If the user wants to see a finished example, attach `ref/example.xlsx` and summarise its sheet list and one test sheet — a chat cannot render Excel.

### `/awp-build` — the real AWP
1. **Collect the material**: scope / engagement letter, planning memorandum, kick-off minutes, prior-year report and AWP, SOPs, organisation chart, system list. Read all of it before writing anything.
2. **Pick the pack**: `python scripts/awp.py list` shows the packs and their modules. If a pack fits the process, use it. **If no pack fits** (a new process such as procure-to-pay or payroll): write a **draft pack** for it in library format (`ref/schema.md` section 3 and its "what validate checks" list; copy the structure of `lib/pack-commercial-leasing.json`; `"version": 0`; no client words — tokens only, with a default that names the policy for every threshold or duration; one module per sub-process in the scope, typically 6-12, in cycle order, each with activities + controls, 3-6 questions, 1-2 risks, a test and an analytic where a listing exists), save it as `pack-<process>.json` in a working folder, `python scripts/awp.py validate <that file>`, then `list`, `compose` (and later `learn`/`apply`) with `--lib <that folder>` (core is still found next to the script; `build` and `verify` read the spec and need no `--lib`; the stamp will say `pack <process> v0 (draft)`). Core gives the control environment, master file, reconciliations, variance analysis and the general closing questions; **exclude the core modules that do not fit** (`"exclude"` in the selection — e.g. `mod.recon_systems` when there is one ERP and no separate operational system, `mod.recon_bank` or `mod.variance_analysis` when they are not in scope) and let the pack carry its own closing modules on the core `reconciliations` sheet. A pack may redefine a core sheet's background (`sheets` with the same id — the later library wins). Deliver the draft pack next to the workbook; the owners publish it (`README.md`).
3. **Write the selection JSON** (`../work/<ClientShort>_<Process>_selection.json`; copy `ref/selection-example.json`; schema in `ref/schema.md`). `python scripts/awp.py list` prints every id and token you can use (core and all packs; a pack name after `list` limits the packs shown). Fill: client, process, period, prefix, packs; **tokens** — every role, system, department and threshold the material names (tokens you leave out take a generic default, and `compose` lists those so you can confirm them); `prior_year` — one entry per risk id that had a prior-year observation (the observation, its rating and management's commitment, two or three sentences; `compose` copies it into the RCM finding cell, the "why we ask" of the questions on that risk's controls and the objectives of its tests); `background_additions` — one paragraph per walkthrough sheet id on what changed in the period (team, systems, events); optional `modules` / `exclude` to narrow the scope.
4. **Compose**: `python scripts/awp.py compose ../work/<ClientShort>_<Process>_selection.json ../work/<ClientShort>_<Process>_spec.json`. It validates the spec as it goes. Read every line it prints: `note:` is a wrong id or an unresolved reference, `warn:` is a content gap, `info:` only lists tokens left at their default.
5. **Deepen and correct** where the material gives you more than the library, or contradicts it. Do it in the selection, not in the 100 KB spec: `overrides` (keyed by library id: change a test's basis or steps, a question's "why", a control's text or activity, a risk's wording, a module's scope areas, or a sheet's background by its sheet id; a field you give replaces the library's whole field, so give the full list when you change one step) and `extra_modules` (engagement-specific modules in library format — a new test and RCM row for a one-off event, say; `compose` numbers and cross-references them like any other module). Then re-run `compose`. Extend risks with the structural causes the material shows; **rewrite any library sentence the material contradicts** (interface frequency, who approves what, where a timeline is counted from) — the spec is the engagement's own document, the library is only its starting point. The RCM quotes each test's steps from the test (the first risk that uses a test carries them; later risks say "Refer to Test n"), so change steps on the test and let the RCM follow. Writing rules and examples are in `ref/content.md`. Never invent client facts; leave `[placeholder]` and list the gap in your report. If the user gave firm sampling guidance, apply it; otherwise use the sizing conventions in the content reference. Editing the spec directly is allowed for anything the selection cannot express, and `validate` checks the result either way.
6. **Validate and build**: `python scripts/awp.py validate ../work/<ClientShort>_<Process>_spec.json` again if you edited the spec by hand (zero errors; clear every warning you can), then `python scripts/awp.py build ../work/<ClientShort>_<Process>_spec.json "../out/<ClientShort> IA FY<yy>_<Process>.xlsx"` (`FY<yy>` = the two-digit year in which the review period ends, e.g. FY27 for a period ending March 2027).
7. **Verify**: `python scripts/awp.py verify "<the workbook>"` must print `VERIFY PASSED` (references, WP refs and feeds, step columns, placeholders and tokens, formulas, scope sections, minimum depth per sheet, stamp). Then read the workbook once with openpyxl for what no script can judge: each scope area is addressed by at least one RCM row, the prior-year points sit where the material put them, and nothing contradicts the material.
8. **Deliver** from `../out/`: the workbook, and the selection + spec JSON copied beside it (kept with the engagement; the user need not open them). Report in a few lines: counts (walkthrough sheets, controls, risks, tests, questions, analytics), sources used, library sentences you corrected, placeholders left, questions for the client. If the user asked for the result in one go, run straight through and report; otherwise pause after step 3 and after step 5 to agree the choices.

### End of engagement — contributing back
Harvesting a finished AWP into the libraries is the **awp-learn** skill, not this one. When the user asks for it, say so and point them to `skill-awp-learn-<version>.zip`; do not hand-edit a library or this skill.

### `/awp-release` — owners only
`python scripts/awp.py check` runs every acceptance test (selftest, library validation, reference build and round-trip, learn idempotence when awp-learn is beside this skill, placeholder and leak scans) and prints `CHECK PASSED`; the rest of the procedure is in `README.md`. If an engagement user asks to change `scripts/awp.py` or `SKILL.md`, decline and point them to the owners.

## Rules that always apply
- The spec is the single source; the workbook is generated. Changes are made in the spec and rebuilt.
- Structure is fixed: RCM, process understanding (activities, performed by, frequency, control reference, control, owner, classification, type, DE finding, document; walkthrough questions with why, documents, interviewee), testing (objective, basis, population, sample size, source, numbered steps, work-done table), DA. Users add depth, never structure.
- Write complete sentences in the house style (examples in `ref/content.md`); name roles, systems, documents and thresholds; risks state the failure **and** the consequence; audit steps are numbered and each is checkable with a document.
- Sample sizes follow the firm's guidance; carry "or all if the population is smaller" where it applies.
- Prior-year observations stay visible: RCM DE-finding cell, walkthrough "why we ask", test objective ("This test also follows up on prior-year Observation n").
- No client data in any library file, ever. Libraries change only through the awp-learn skill or the owners.

## Files
- `SKILL.md` — this file. `README.md` — maintainers' notes (release steps, design decisions); `CHANGELOG.md`.
- `scripts/awp.py` — selftest / list / template / compose / validate / build / verify / export / diff / check. `--lib FOLDER` adds a folder of libraries (draft packs).
- `lib/core.json`, `lib/pack-commercial-leasing.json` — content libraries (versions inside). In the repository they live in `../awp-lib/`, shared by every `awp-*` skill; the release zip carries a copy.
- `ref/layout.md` — the sheet layouts and formatting the script enforces.
- `ref/schema.md` — selection, spec and library JSON, every field; token table; what `validate` checks.
- `ref/content.md` — how to write each element, with generic house examples.
- `ref/copilot.md` — running this in corporate Copilot.
- `ref/selection-example.json` — a complete selection for a fictitious client; copy it to start a new one.
- `ref/example.xlsx` — the workbook built from that selection: exactly what every build looks like. Attach it (with a short summary) to a user who asks what they will get.
